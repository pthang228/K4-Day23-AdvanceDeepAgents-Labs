# Tool Use in LLM Agents: Foundations, Evaluation, Reliability, and Standardization

## TL;DR

- The field moved from prompt-level reasoning-and-acting loops to self-supervised API learning and then to schema-enforced function calling: ReAct interleaved reasoning traces with actions over a simple Wikipedia API and reported +34% and +10% absolute success on ALFWorld and WebShop with one or two in-context examples [1], while Toolformer trained a model self-supervised, with nothing more than a handful of demonstrations per API, to decide which APIs to call and when [2].
- Benchmarks show tool-using agents remain far from reliable on multi-step work: WebArena's best GPT-4-based agent reached 14.41% end-to-end task success against 78.24% human performance [3], and τ-bench reports that even state-of-the-art function-calling agents such as gpt-4o succeed on fewer than half of the tasks and are quite inconsistent, with pass^8 below 25% in retail [4].
- The dominant retrieved security risk is indirect prompt injection compounded by excessive agency: trusted instructions and untrusted observations share one context [5], a zero-click exploit (CVE-2025-32711) exfiltrated data from Microsoft 365 Copilot via a single crafted email [6], and OWASP ranks prompt injection first and roots excessive agency in excessive functionality, permissions and autonomy [7].
- Measurement itself is contested: one audit found 18.5% evaluator–human misalignment across 496 expert-reviewed tasks and an 18.9-point run-to-run spread in LiveMCPBench [8], and a corrected harness reported 21.7% attack success under tool-identity scoring where the true argument-level rate was 1.2% [9].
- Standardization is the clearest recent change — MCP in November 2024 and A2A in April 2025 [10][11] — yet tool catalogs scale badly, and retrieval-based pruning reportedly tripled tool-selection accuracy (43.13% versus 13.62%) while cutting prompt tokens by over 50% [12].

## Background

Two 2022 results supply the substrate for everything that follows. Chain-of-thought prompting showed that few-shot exemplars of the form ⟨input, chain of thought, output⟩ elicit multi-step reasoning without any fine-tuning: one PaLM 540B checkpoint with eight exemplars reached state-of-the-art GSM8K accuracy, surpassing a fine-tuned GPT-3 with a verifier, and the ability is reported as emergent at roughly 100B parameters [13]. ReAct then interleaved reasoning traces with task-specific actions so the model could interface with external sources such as a simple Wikipedia API, framed as prompt-based few-shot learning, with the authors noting that prompted ReAct has limited support for reasoning/acting behaviors and that larger action spaces require more demonstrations than in-context length limits allow [1].

A second strand argued that the language model alone is insufficient. MRKL, from AI21 Labs, describes large language models as "inherently limited" with output "in many cases wrong", and proposes a modular neuro-symbolic architecture in which neural models are complemented by discrete knowledge and reasoning modules, implemented as Jurassic-X [14]. Toolformer turned API invocation into a learning target: the model learns which APIs to call, when to call them, what arguments to pass, and how to incorporate results into future token prediction, using self-supervision with only a handful of demonstrations per API across a calculator, a QA system, two search engines, a translation system, and a calendar; the reported outcome is substantially improved zero-shot performance on many downstream tasks, often competitive with much larger models [2].

A third strand grounded tool use in retrieval and browsing. WebGPT fine-tuned GPT-3 with a text-based browser that issues commands such as "Search ...", "Find in page: ..." or "Quote: ...", trained by copying human demonstrations and then optimizing a reward model of human preferences through reinforcement learning or rejection sampling; the best model's answers were preferred 56% of the time over human demonstrators on ELI5, and the model must cite sources so users can check factual accuracy [15]. A 2024 survey consolidates these strands into one loop — understand the instruction, decompose it into subtasks, dynamically adjust the plan through reasoning, then select appropriate tools per subtask — and names trustworthy tool use, tool creation with foundation models, and personalization as open problems [16]. A more recent survey organizes agentic work into reasoning, acting (action models, robots, tools) and interacting (multi-agent systems), reporting that the categories reinforce one another: retrieval enables tool use, reflection improves multi-agent collaboration, and reasoning benefits all categories [17].

## How agents are given tools: prompting, learning, and interfaces

The first generation of tool-using agents was purely prompt-based. ReAct's interleaving of reasoning traces and actions was shown to beat imitation and reinforcement-learning methods by 34% and 10% absolute success on ALFWorld and WebShop respectively with only one or two in-context examples [1]. That result has since been contested: a sensitivity analysis along ReAct's own claims found that performance was minimally influenced by interleaving reasoning traces with action execution, contrary to the original claims, and attributed the observed gains to similarity between the input example tasks and the queries (approximate retrieval) rather than to inherent reasoning, which increases the prompt designer's cognitive burden [18].

Self-supervised tool learning offered a different route, decoupling capability from prompt engineering by training the model to insert API calls itself in a self-supervised way that requires nothing more than a handful of demonstrations per API [2]. Learned tool use subsequently became a product interface: OpenAI's APIs declare tools as JSON schemas in a `tools` parameter, and strict mode builds on the platform's structured-outputs feature and requires `additionalProperties: false` for each object in those parameters [19]. The same platform supports pairing function calling with tool search, which defers rarely used tools and loads them only when the model needs them [19]. The practical arc is therefore from demonstrations and rewards [1][15], through self-supervision [2] and neuro-symbolic modularity [14], to declarative schema contracts enforced at the API boundary [19].

## Benchmarks: what is measured and what the numbers show

Tool-use evaluation splits into two families. The first measures API selection and argument construction. ToolBench collects 16,464 real-world RESTful APIs spanning 49 categories from RapidAPI Hub, with single-tool and multi-tool instructions, and is scored by an automatic evaluator (ToolEval) reporting pass rate and win rate with stated human agreement of 87.1% and 80.3% respectively; the same work reports Vicuna and Alpaca at zero pass and zero win rate, ChatGPT with DFSDT averaging 64.8 pass versus GPT-4 with ReACT at 57.2, and Claude-2 with ReACT averaging only 6.8 [20]. The Berkeley Function Calling Leaderboard combines single-turn crowd-sourced items (2,251 items drawn from more than 67,000 contributed datapoints), a multi-turn split with eight API suites and 1,000 queries, and agentic splits, using AST substring matching as a scalable proxy for execution [21].

The second family measures task outcomes in interactive environments. τ-bench simulates dynamic conversations between a language-model user and an agent that is given domain-specific API tools plus policy guidelines, and compares the database state at the end of the conversation with an annotated goal state, with a pass^k metric for consistency across k independent trials [4]. WebArena provides fully functional websites from four domains — e-commerce, social forum, collaborative software development and content management — plus tools and external knowledge bases, and scores long-horizon tasks by functional correctness [3]. AgentBench evaluates 29 API-based and open-source models across eight distinct interactive environments, finding that top commercial LLMs act strongly as agents while open-source competitors no larger than 70B lag significantly [22].

Reported success rates are low and decay with horizon or repetition. WebArena's best GPT-4-based agent completes 14.41% of tasks end-to-end versus 78.24% for humans [3]. On τ-bench, even state-of-the-art function-calling agents such as gpt-4o succeed on fewer than half of the tasks and are quite inconsistent, with pass^8 below 25% in retail [4]. BFCL's own paper states the tension directly: while state-of-the-art LLMs excel at single-turn calls, memory, dynamic decision making and long-horizon reasoning remain open challenges [21].

## Reliability limits, error propagation, and measurement noise

Across the retrieved benchmarks the failure modes converge: long-horizon reasoning, memory, decision-making, and rule or instruction following recur as stated obstacles [22][21]. The reliability evidence extends into the parameters of individual calls. AgentProp-Bench, built from 2,000 tasks, 2,300 traces and nine production LLMs with a 100-label human-validated subset, reports that a parameter-level injection propagates to a wrong final answer with a human-calibrated probability of about 0.62 (range 0.46–0.73), and that a tuned runtime interceptor reduces hallucination on GPT-4o-mini by 23.0 percentage points but has no significant effect on Gemini-2.0-Flash — a strong hint that runtime mitigations do not transfer across models [23].

A second, less discussed reliability problem is the evaluator. The same benchmark found substring-based judging agrees with human annotation at kappa = 0.049, i.e. chance level, while a three-LLM ensemble reaches kappa = 0.432 [23]. An independent validity audit of four benchmark families (BFCL v4, τ2-Bench, LiveMCPBench, MCP-Atlas) recorded 92 evaluator–human disagreements across 496 expert-reviewed tasks, an 18.5% misalignment rate, with deterministic benchmarks showing brittle state matching, trajectory lock-in and incorrect ground truths, and LLM-judge benchmarks showing rubric drift, hallucinated completion, answer-only scoring and run-to-run variance; in LiveMCPBench, 23 repeated evaluations of the same setup scored between 57.9% and 76.8%, an 18.9-point spread the authors describe as large enough to change leaderboard conclusions [8]. These findings argue that reported tool-use numbers are evaluator-dependent rather than comparable across suites.

## Security and safety of tool access

The retrieved security evidence converges on indirect prompt injection as the central structural risk. OWASP ranks prompt injection (LLM01) first among LLM application risks, requiring ongoing model and safety updates because prevention is not solved, and its LLM06 entry — excessive agency — names excessive functionality, excessive permissions and excessive autonomy as root causes; triggers include direct and indirect prompt injection from a malicious user or a compromised extension or peer agent, with impacts across confidentiality, integrity and availability [7]. A complementary framing describes the "lethal trifecta": access to private data, exposure to untrusted content, and the ability to communicate externally. Combining all three lets an attacker steal data; a single tool such as the GitHub MCP server can supply all three legs, since public issues are untrusted input, private repositories are the data, and pull requests provide the exfiltration channel. Removing any one leg prevents the attack, and because filter-based defenses are probabilistic the author's stated position is that "99% filtering is a failing grade", motivating a Dual-LLM privileged/quarantined split [24].

Production evidence exists. EchoLeak (CVE-2025-32711) documents a zero-click prompt injection in Microsoft 365 Copilot that enabled remote, unauthenticated data exfiltration via a single crafted email, chaining evasion of Microsoft's XPIA cross-prompt-injection classifier, circumvention of link redaction using reference-style Markdown, exploitation of auto-fetched images, and abuse of a Teams proxy permitted by the content security policy; its recommendations are prompt partitioning, enhanced input/output filtering, provenance-based access control, strict content security policies, and least privilege [6]. Research defenses emphasize authorization over content inspection. ToolFence argues that tool-using agents stay vulnerable precisely because trusted instructions and untrusted observations share one context, and that multi-path consensus defenses still leave high attack success because they inspect content rather than effects — including "within-tool" attacks that keep the intended tool but manipulate its arguments; on AgentDojo with Qwen3-max, ToolFence reduces the overall attack success rate to near zero at a cost of a 3.80 percentage-point drop in clean utility, and notes that CaMeL offers stronger guarantees at substantial latency cost [5]. On the platform side, the OS-enforced sandbox for a coding agent restricts filesystem and network access for shell commands — restrictions that hold "even if an allowed command does more than its name suggests" — but covers shell commands only, leaving file tools, MCP servers, hooks and helpers outside it with the user's full access; permission rules ordered deny > ask > allow are evaluated before any tool runs and are enforced by the harness rather than by the model, so sandbox restrictions still apply if a prompt injection bypasses the model [25]. OWASP's recommended mitigations align with this authorization-centric view: minimize extensions, functionality and permissions, avoid open-ended extensions, execute in the user's context, require human approval, and apply complete mediation in downstream systems [7].

Benchmark-level evidence for injection defenses should be treated cautiously. A validated harness auditing an indirect-prompt-injection benchmark named four defect classes — silent payload non-delivery, attack success scored by tool identity rather than arguments, false rejection conflated with incapacity, and no audit trail — and, re-scoring identical traces, found that the tool-identity scorer reported a 21.7% attack-success rate where the true argument-level rate was 1.2%; a model previously reported at 62.8% registered 0% under the corrected harness [9]. Consistent with that, AgentProp-Bench's chance-level substring agreement (kappa = 0.049) shows how weak some judging is under the hood [23].

## Standardization and scaling: protocols, retrieval, and budgets

The most visible recent change is the move from ad-hoc tool wiring to open protocols. Anthropic open-sourced the Model Context Protocol in November 2024 as "a new standard for connecting AI assistants to the systems where data lives", shipping the specification and SDKs together with local MCP server support and pre-built servers for Google Drive, Slack, GitHub, Git, Postgres and Puppeteer, with the stated aim of replacing fragmented per-source connectors [10]. Google announced A2A in April 2025 with contributions from more than 50 technology partners, explicitly positioned as complementary to MCP, which "provides helpful tools and context to agents", while A2A itself targets agent-to-agent task delegation [11]. A comparative survey of MCP, ACP, A2A and ANP frames the motivation plainly — ad-hoc integrations are difficult to scale, secure and generalize across domains — and proposes a phased roadmap: MCP for tool access, then ACP for messaging and discovery, A2A for collaborative task execution, and ANP for decentralized agent marketplaces [26].

Scaling is the counter-trend. RAG-MCP states that LLMs struggle to use a growing number of external tools such as those defined by MCP because of prompt bloat and selection complexity, and retrieves only the most relevant tool descriptions from an external index before calling the model; on its benchmark tasks, including an MCP stress test, this cut prompt tokens by over 50% and more than tripled tool-selection accuracy (43.13% versus a 13.62% baseline) [12]. Independent measurement points the same way: in a benchmark over ToolE queries across eight popular LLMs, the correct-selection rate of almost all models decreased as the tool list grew, particularly from the top 5 to the top 10 tools, and most models struggled to recognize their own capability boundaries [27]. Budget rather than raw capability can also bind: one study finds that simply granting an agent a larger tool-call budget fails to improve performance because agents lack budget awareness and quickly hit a performance ceiling, and proposes a Budget Tracker plug-in with a test-time scaling method that decides whether to dig deeper on a lead or pivot; it formalizes a unified cost metric jointly accounting for token and tool consumption and reports more favorable cost-performance curves [28].

Finally, the protocol layer is itself now a security surface. A systematization of knowledge calls MCP the "de facto standard" for connecting LLMs to external data and tools and the "USB-C for Agentic AI", taxonomizes adversarial threats (indirect prompt injection, tool poisoning) separately from epistemic safety hazards such as alignment failures in distributed tool delegation, and analyzes how MCP's Resources, Prompts and Tools primitives let "context" be weaponized to trigger unauthorized operations in multi-agent environments; defenses surveyed range from cryptographic provenance to runtime intent verification [29].

## Trends and open problems

Three shifts are well evidenced in the retrieved set. First, interfaces standardized: MCP (November 2024) and A2A (April 2025) turned tool and context access into a protocol problem rather than a per-application integration problem [10][11], with surveys treating them as complementary layers [26] and analysis already treating MCP as the default tool layer whose primitives carry new risk [29]. Second, cost became a first-class concern: agents that lack budget awareness hit a performance ceiling when simply granted larger tool-call budgets, and cost must be accounted for jointly across tokens and tool calls [28]. Third, evaluation skepticism grew alongside capability claims: judge agreement can sit at chance level [23], benchmark validity problems can shift leaderboard conclusions [8], and defense-success numbers are highly sensitive to how success is scored [9].

Unresolved and disputed issues are equally visible. Reliability at horizon remains the headline gap: BFCL's own authors state that long-horizon reasoning and dynamic decision making are open challenges even as single-turn calls are largely solved [21], τ-bench's pass^k decay shows that consistency, not average success, is the binding constraint [4], and AgentBench records instruction following and long-term reasoning as outstanding obstacles [22]. Whether reasoning-and-acting prompting truly causes the reported gains is disputed: the original ReAct work attributes them to interleaving [1], while a later sensitivity analysis attributes them to exemplar–query similarity instead [18]. On safety, the retrieved sources disagree in emphasis rather than in fact — content-filtering defenses are called probabilistic and insufficient [24], consensus-based content inspection is reported to keep attack success high because it inspects content rather than effects [5], while fine-grained authorization reports near-zero attack success at a 3.80 percentage-point utility cost [5] and the corrected harness shows how much of the apparent attack surface was measurement artifact [9]. Named open problems across the retrieved surveys are trustworthy tool use, tool creation by foundation models, personalization [16], and the safety, liability and security of assistants taking action in the real world [17]. Scaling is unsolved in complementary ways: catalogs degrade selection accuracy [27], retrieval prunes prompt bloat but presumes a good index [12], and larger budgets alone do not help without budget awareness [28].
